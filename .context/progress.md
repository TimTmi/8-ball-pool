# Progress: 8 Ball Pool

## Current State
- Unity Project folder structure has been set up.
- UI Toolkit assets (UXML/USS) for Main Menu, Gameplay, and Credits created.
- Basic UI Controllers implemented.
- Main Menu and Gameplay scenes instantiated and added to Build Settings.
- Phase 2 Core Gameplay Mechanics implemented: InputManager captures drag input, GameplayUIController exposes lock toggles, shoot button, and spin control.
- **Phase 3 (Partial): Visual & Physics Setup** - Procedural generation of 2D pool sprites (felt, cushions, pockets, 16 balls, cue stick) added via Editor script. `TableSetup` dynamically builds the physics and visual layout at runtime using authoritative constants from `TableLayout`.
- **Phase 3 (Partial): Shot Physics & Cushion Bounce** - `CueController` (on the Table object) launches the cue ball from aim angle + power, and reports when every ball has come to rest. `Ball` owns each ball's motion state and snaps near-zero velocity to a full stop. `Cushion` drains the surplus rebound energy on rail hits. Aiming and the cue stick are suppressed while the shot plays out.
- Collider sizing in `TableSetup` was corrected: ball, pocket, and rail colliders are now authored in local space, so they match their sprites instead of being scaled to the wrong size by the transform.
- **Phase 4 (Partial): Pocketing** - The rails are now six runs with a mouth at every pocket, so balls can physically enter one. `Pocket` captures a ball when its centre reaches the hole; `Ball.Drop()` takes it out of play with a short sink. A scratched cue ball is returned to the head spot once the table settles.
- Aim/power controls rewritten (2026-08-31, same-side scheme): aim angle = direction from pointer through the cue ball (finger drags on the cue's side, pull-back style), power = pointer-to-cue-ball distance (full power at `TableLayout.HalfFeltWidth`, tunable via `_maxPowerDistance`). Replaces the old drag-delta scheme.
- Pull distance made 1:1 (2026-08-31): pointer-to-cue-ball distance now maps directly to the cue stick pull-back, capped at `_maxPullDistance` (default 2.5u) in `InputManager`, which also defines full power. The cue visual reads the same field, replacing its own hardcoded 2.5u pull. Remapped 2026-09-01: power is 0 at the cancel-zone edge, so pointer distance beyond `_cancelRadius` maps 1:1 to pull (full power at cancel radius + max pull) — previously hitting the zone edge already read 24% power.
- Cue sprite orientation fixed (2026-08-31): cue art now has the tip (chalk) on the right (+X), matching the runtime assumption that the sprite's +X axis points at the cue ball (`InputManager.UpdateCueVisuals`). Previously the butt faced the ball.
- HUD press isolation fixed (2026-08-31): `GameplayUIController.IsPointerPressOnUI` marks presses that belong to the HUD (shoot button, lock toggles, spin button/panel, or the tap that closes the spin panel); `InputManager` ignores them for aim/power. Replaces the narrower `IsSpinInteracting` flag, which is deleted.
- Locks cleared on turn end (2026-09-01): `GameplayUIController.UnlockAimAndPower()` unticks both lock toggles, called from `InputManager.HandleShoot` after a successful shot, so each new turn starts with aim and power unlocked.
- Drag cancel zone (2026-09-01): `InputManager` snapshots aim/power/has-aim when a drag starts; while the pointer stays within `_cancelRadius` (serialized, default 0.6u) of the cue ball, aim and power revert to the snapshot, and releasing inside the zone cancels the drag (no shoot button). Dragging back out of the zone resumes aiming. Second cancel zone (2026-09-01): a margin of `_edgeCancelMargin` px (serialized, default 48) along the app's screen edges behaves identically (`IsPointerInCancelZone` = cue-ball zone OR screen-edge zone).
- Power bar (2026-09-01): while dragging with power unlocked, a world-space bar (`PowerBar` component, spawned as a Table child by `TableSetup.SetupPowerBar`) floats below the cue ball and fills 0→1 with `CurrentPower`. `InputManager.UpdatePowerBar` owns visibility (dragging + not power-locked + table settled) and hides it otherwise.
- Rail look reworked (2026-09-01): brighter wood rail (dark runtime tint removed from `TableSetup.SpawnRail`) plus a darker-green cushion pad strip (`RailCushion` sprite, `TableLayout.CushionPadThickness`) spawned on the felt-facing edge of each rail run by `TableSetup.SpawnCushionPad`; visual only, collider unchanged.
- Closed rail frame (2026-09-01): rail wood now runs past every pocket so the six segments join into a complete rectangular frame with the pocket holes cut into it. `TableLayout.RailSegment` gained `VisualCenter`/`VisualSize` (full wooden run) alongside `Center`/`Size` (cushion-only span); `TableSetup.SpawnRail` scales the sprite to the visual run and offsets/shrinks the BoxCollider2D to the cushion span, so pocket mouths stay physically open.
- Rounded table corners (2026-09-01): `SpriteGenerator.GenerateRailCorner` produces a wood corner cap rounded at its outer corner (0.25u arc, highlight rim); `TableSetup.SetupRailCorners`/`SpawnRailCorner` place four rotated caps over the square rail-run corners (sortingOrder -7). Visual only, colliders unchanged. Pocket sprites raised to sortingOrder -6 so the holes draw above the caps. Rail visual runs were shortened to stop at the felt edges (`TableLayout` longVisualLength = HalfFeltWidth, side height = FeltHeight) so the wood doesn't show through the caps' rounded notches; the caps alone close the corners.

Felt (9×4.5, 2:1), rail thickness 0.4u (~9% of playing width), and spots unchanged — they already matched. `SetupPhysicsPrefabs` editor script now reads `TableLayout` instead of hardcoded sizes. Straight-line only: no spin, no cue-ball path after contact, no rail bounce. Dots and ghost carry a thin baked-in outline (`_outlineWidth`, 0.006u — under a screen pixel at ortho 4) so they read against the felt. Compiles clean; not run.

- Spin (2026-09-01): `SpinModel` holds the formulas, shared by the live shot and the preview. `GameplayUIController.ResetSpin()` (called from `StrikeAndShoot` after a successful shot) recentres `CurrentSpin` and both dots, so spin never carries into the next turn. Top/back spin fires on the first ball struck (`CueBallSpin`), side spin curves the roll and swings the rebound off a rail (`Cushion` owns that so the two callbacks cannot race). Direction follows the 8 Ball Pool guide: left spin moves the ball left. Measured: 5.3 degrees of curve at full side spin, power-independent; ±19.3 degrees of cushion swing; back spin reverses a full hit at 0.45x impact speed. `ShotPrediction` became a stepped walk at `Time.fixedDeltaTime` (a coarser clock drew the line 0.22u long), and `AimLine` now draws the post-contact cue path in a third colour. Compiles clean; not run.

- Post-contact trail fix (2026-09-01): the cue-ball-after-contact run was drawn but never appeared. `ShotPrediction` resumes the walk from a point touching the ball it just struck, and `CastAhead` only excluded the cue ball, so the next cast hit that same ball at zero distance and — with `contacted` already true — took the "rail or second ball" branch and broke out. The path ended up one point long, below the two `PlaceDotsAlong` needs. `CastAhead` now takes a second collider to ignore, set to the struck ball at first contact. Measured: 1.0u of trail (5 dots) for every cut angle and spin, and correctly nothing for a dead-straight stun.

- Pseudo-3D ball roll (2026-09-03, on `feat/pseudo-3d-ball-roll`): balls no longer render as flat sprites. `Assets/Shaders/BallRoll.shader` treats each pixel of the sprite quad as a point on a hemisphere, rotates it into the ball's orientation and samples the equirectangular `BallMap_XX` maps (the flat `Ball_XX` sprite stays only as the quad/UV provider). `BallRoll` (Gameplay, added by `TableSetup` to every ball) integrates the orientation in `FixedUpdate`: rolling ω = (ẑ×v)/r from rigidbody velocity, plus the cue ball's `CueBallSpin.SideSpin` as a pivot about the vertical axis (`MaxVerticalSpinRate` 5 rad/s at full side, sign is aesthetic and easy to flip). Orientation reaches the shader as a conjugate quaternion via `MaterialPropertyBlock` (`_Rotation` + `_MapTex`) against one shared material — `TableSetup` looks the shader up by name unless `_ballRollShader` is assigned in the Inspector (Shader.Find means it must be pinned for real builds). `Rigidbody2D.freezeRotation = true` so collision impulses no longer spin the flat sprite on top of the fake sphere; `Ball.IsMoving`'s angular check is therefore dead (harmless). Sink fade/tints still work — the shader multiplies sprite vertex color. Not compiled/run (no Unity CLI); needs play-test of roll direction, shading, and map sliding.

## Rules system (2026-09-02, on `feat/game-rules`)
- Component-pluggable rules (`EightBall.Rules` namespace, `Assets/Scripts/Rules`): each rule is a MonoBehaviour implementing `IShotRule.Evaluate(ShotReport, GameState, RuleFindings)`; `RulesController` (on the Table object) discovers them with `GetComponents<IShotRule>()`, so add/remove in the Inspector = add/remove rule. Minimal scope shipped: `GroupAssignmentRule`, `TurnContinuationRule` (scratch → opponent + ball in hand), `EightBallBreakRule` (8 on break respotted to foot spot, no verdict) and `EightBallWinRule` (8 after group cleared wins; early/with scratch loses — ignores the first shot, so it is order-independent of the break rule). `BallGroups.WasPotted(shot, n)` is the shared shot-membership check.
- Fact seams: `Ball.OnPocketed` event (fired in `Drop()`, covers pockets and the out-of-bounds failsafe) and `CueController.OnShotStarted`. `ShotRecorder` (Table component) subscribes to ball pocket events during a shot and re-emits one `OnShotRecorded(ShotReport)` at settle, so rules never race Unity's callback order. `CueController.ReturnScratchedCueBall` was deleted — the cue ball now comes back only via rules.
- `TurnManager` demoted to executor: no more settle subscription or unconditional flip; `BeginTurn(int)` applies the rules verdict and still raises `OnTurnStarted` (InputManager/UI unchanged). `RulesController` (Table component) feeds the frozen `ShotReport` to every `GetComponents<IShotRule>()`, applies findings, and owns ball-in-hand: after a scratch the cue ball is restored on the head spot and `IsBallInHandPending` gates aiming (`InputManager` placement mode drags the ball, tints red over illegal spots, commits on a legal release via `CompleteBallInHand`). Safety net restores a pocketed cue ball if the scratch rule is removed.
- Game-over UI: `GameplayUIController.ShowGameOver` shows a full-screen `game-over` overlay (winner-coloured title, Play Again → reload Gameplay, Menu → MainMenu); `SetShootDeniedHint(string)` swaps the shoot-hint text (null restores default), so a ball-in-hand turn says "Ball in hand — drag the cue ball to a legal spot".
- Scene wiring: `ShotRecorder`, `RulesController`, `GroupAssignmentRule`, `TurnContinuationRule`, `EightBallWinRule`, `EightBallBreakRule` added to the Table object in `Gameplay.unity` (hand-written YAML with new script GUIDs in the created `.meta` files) — **verify in the Editor that the six components appear on Table with no missing-script warnings**.
- EditMode tests: `Assets/Tests/Editor/RulesTests.cs` (no asmdef — lives under an `Editor` folder so it lands in Assembly-CSharp-Editor; NUnit via com.unity.test-framework 1.7.0). Fabricated `ShotReport` scenarios: break pots keep the table open, group assignment, scratch → ball in hand, open-table continuation, early 8 / scratch+8 / last-group-ball+8 losses, 8-on-break respot (break rule), win rule silent on the break.
- **Nothing compiled or run** (no Unity CLI); all rules math is unit-testable but requires the user to open Unity, let it import the new scripts/metas, and run the EditMode tests + a play-test.
